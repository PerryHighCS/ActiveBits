- Date: 2026-09-24

## Public and SyncDeck child participant IDs

- Date: 2026-09-24
- Area: waiting-room entry | SyncDeck embedded and solo child sessions
- Contract: Public live and persistent entry stores always mint an ID; request `participantId` is ignored. The separate trusted store function accepts an explicit ID only after the SyncDeck parent session's accepted-entry cookie resolves to an accepted student (embedded routes also require a current roster record). Embedded WS delivery and recovery HTTP routes require this parent proof before issuing a child-scoped token. The solo child entry route derives its ID (and fallback display name) from the parent's accepted-entry record, not the request body, and does not require a roster record because standalone students never open the SyncDeck WebSocket. It does not yet verify that the child belongs to the parent; see the solo child binding design in `.agent/plans/shared-activity-runtime-authentication.md`.
- Validation: `server/entryParticipants.test.ts`; `server/sessionEntryRoutes.test.ts`; `server/persistentSessionRoutes.test.ts`; `activities/syncdeck/server/routes.test.ts`; `activities/syncdeck/playwright/student-return.spec.ts`.
- Follow-up: #313 must make the shared entry and child-token writes safe against concurrent whole-session writers.

## SyncDeck student transport authority

- Date: 2026-09-24
- Area: SyncDeck student WebSocket | embedded-context | embedded auto-activation
- Contract: The parent accepted-entry cookie resolves the student ID at WebSocket admission, including first roster registration. A client `studentId` may confirm that identity but cannot choose another roster student. Embedded-context and auto-activation require the same cookie plus a matching ID hint. Missing, wrong-session, or mismatched proof fails before student state is replayed or child state is mutated. WebSocket 1008 `forbidden` (and `missing studentId` / `unregistered student`) tells the student client to clear every stored identity for the session (sessionStorage and localStorage, via `clearSyncDeckStoredStudentIdentity`) and recover from `GET /api/syncdeck/:sessionId/student-identity` → `{ studentId, displayName }` (403 without a valid accepted-entry cookie, `no-store`). The client adopts that identity unless it equals the ID just rejected (`resolveRecoveredSyncDeckStudentIdentity`), so recovery cannot loop; the same lookup runs on load when nothing usable is stored, because a reload with a valid cookie skips the waiting room. Browser storage is only a cache; the cookie is authoritative.
- Validation: `activities/syncdeck/server/routes.test.ts`; `activities/syncdeck/client/student/reconnectUtils.test.ts`; `activities/syncdeck/playwright/student-return.spec.ts`.
- Follow-up: #313 must make SyncDeck roster/session writes atomic alongside shared entry writes.

## Resonance draft-saving rewrite: single run-identity form, parent-owned retry, server-resolved drafts

- Date: 2026-09-17
- Context: A prior branch (PR #375, never merged) tried to fix issue #374 — an unconfirmed draft is lost if the student switches stack tabs before it saves, because `QuestionView` (the only thing that tracked it) is remounted per question id — by adding an ever-growing legacy/canonical run-identity bridge and a generation-numbered retry queue, and grew to 76 commits / +6,850/-248 lines while still not reaching a stable fixed point (three consecutive review rounds surfaced the same "resolved scalar loses its form" defect). - Contract (single run-identity form): `activeQuestionRunRevision: number | null` is now the *only* run identity everywhere. `matchesActiveQuestionRun` (routes.ts) dropped its `legacyStartedAt` parameter and the revision-1/timestamp-coincidence branch; `draftMatchesCurrentRun` and `isStaleActiveResponse` dropped their "`activeQuestionRunRevision` field absent → fall back to a timestamp comparison" branches; `Response.activeQuestionRunRevision` and `responseDrafts[key].activeQuestionRunRevision` are now required (`number | null`, never `undefined`) in both the shared type and the server's normalization functions. `activeQuestionRunStartedAt` remains in the wire shape only for deadline math/display and is never compared for identity again (client-side `hasActiveQuestionRunRestart`, `buildEditSequenceKey`/`resolveCurrentEditSequence`/`advanceEditSequenceForRevisit` call sites, and `QuestionView`'s own run-token all dropped their `activeQuestionRunRevision ?? activeQuestionRunStartedAt` fallback).
- Contract (draft delivery ownership): `QuestionView` no longer persists or retries drafts itself — it only renders the input, calls `onDraftChanged` synchronously on every edit, and handles the explicit "Submit" REST call. `ResonanceStudent` (not `QuestionView`) now owns sending and retrying drafts, because it has the activity-mount lifetime needed to survive `QuestionView` remounting on every stack-tab switch: `unconfirmedQuestionIdsRef` marks a question dirty in `onDraftChanged`, and a `DRAFT_RETRY_INTERVAL_MS` (1s) interval (`selectUnconfirmedDraftQuestionIds`) resends each unconfirmed active question's *current* `submittedAnswers[questionId]` value (read fresh every tick, never a captured historical payload) via `saveDraft`, clearing the "unconfirmed" mark only once an ack matches (content-compared via `isSameAnswer`, exported from `QuestionView.tsx`) the value most recently sent. Because every retry sends the current value, a retry can never race an edit into producing a wrong result — no generation counters or ordering bookkeeping needed. `useResonanceSession.saveDraft` correspondingly dropped its own reconnect-replay queue (`queuedDraftRetriesRef`/`retryDraftSavesRef`): it now just attempts once over the current socket and resolves `false` otherwise, since the parent's periodic retry already guarantees a resend attempt regardless of reconnect timing.
- Contract (server-resolved drafts): `StudentSessionSnapshot` gained `draftAnswers: Record<string, AnswerPayload>` — the viewer's own unsubmitted, current-run draft per active question (`buildStudentSnapshotWithMode`, filtered through the same `draftMatchesCurrentRun`). `ResonanceStudent` merges it into local `submittedAnswers` state underneath `submittedAnswers` (server-submitted) and `current` (locally already-known), so a fresh page load or a remounted `QuestionView` can recover an in-progress edit from the server instead of depending solely on client-cached state.
- Contract (run-restart answer reset): when a question's run restarts or it's reactivated (`ResonanceStudent`'s existing `reactivatedIds`/`didRunRestart` detection), its cached `submittedAnswers[questionId]` entry is now deleted (`resetAnswersForRestartedQuestions`) and it's dropped from `unconfirmedQuestionIdsRef`, not just unlocked via `submittedQuestionIds`. Without this, a stale prior-run answer would both wrongly prefill the reopened `QuestionView` and get resent to the server as a "current" draft under the new run's revision by the retry loop.
- Compatibility constraints: None — this is a from-scratch reimplementation on a branch that never shipped PR #375's shapes, so there is no deployed client/server pair that needs bridging.
- Validation: `activities/resonance/client/student/ResonanceStudent.test.ts` — "an unconfirmed draft on a backgrounded question tab is retried and saved after its QuestionView unmounts" (the #374 regression test; confirmed to fail with the retry loop disabled), "selectUnconfirmedDraftQuestionIds retries an unconfirmed question but not a submitted or already-confirmed one", "resetAnswersForRestartedQuestions drops a restarted question's cached answer, leaving others untouched". `activities/resonance/server/routes.test.ts` full suite green against the simplified identity functions (existing fixtures updated to always set `activeQuestionRunRevision` explicitly instead of relying on the removed undefined/timestamp fallback).
- Follow-up (CodeRabbit review on PR #381, 2026-09-17), three genuine gaps in the above design, all fixed:
  1. **Edit-triggered send, not interval-only.** The 1s retry interval fires on a fixed schedule from mount, not re-armed by edits, so an edit made shortly before a deadline could wait past it for the next tick with zero send attempts. Added `DRAFT_EDIT_DEBOUNCE_MS` (400ms): `onDraftChanged` now also schedules a short per-question debounce (`scheduleDraftSend`) that calls the same `attemptDraftSend` the interval uses. Separately, `attemptDraftSend` no longer skips sending once the client's own clock reads past the deadline — the server's own `update-draft` deadline check is the actual authority, and a rejected late send is a harmless no-op, so guessing "too late" client-side only risked dropping an edit still in flight at the boundary.
  2. **Ack matched to what was actually sent, not just its content.** `attemptDraftSend`'s ack continuation now captures `sentRunRevision`/`sentEditSequence` at send time and only clears the unconfirmed marker if the *current* run revision and edit sequence (at ack time) still match those, in addition to the existing `isSameAnswer` content check. Content equality alone couldn't tell a late ack for a superseded run's send apart from one for the current run's send if the student retyped the same text after a restart — that stale ack would otherwise wrongly clear the new run's still-unsent draft.   3. **Deadline reconciliation.** `useResonanceSession.saveDraft`'s `ws.onclose` now settles every pending `pendingDraftSavesRef` entry with `false` (and clears its timeout) immediately instead of leaving it to the 2s ack timeout — `ResonanceStudent` treats a question as in-flight until that promise settles, so leaving it pending delayed that question's next retry by up to the full timeout after a disconnect. ## Resonance client draft transport state consolidation (2026-09-24)

- Owner: Codex
- Contract: `ResonanceStudent` owns one `QuestionDraftState` record per question for unconfirmed status, the revision when the answer became dirty, the current send-attempt token, and a retry request made while that attempt is in flight. `clearDraftTracking` clears those four fields together on submission, run change, or successful deadline reconciliation. An acknowledgement only clears `unconfirmed` after matching the current run, edit sequence, and answer; it does not abandon the rest of the record. A settlement may clear an in-flight token only when it still owns that token.
- Separate lifecycle: `editSequenceByKeyRef` remains keyed by question and run and is reset only with session/student identity. The session's `responseDrafts` and `draftOrderingWatermarks` remain separate because a watermark must survive deletion of a cleared draft.
- Known limitation and scope decision: This client-only consolidation does not make Resonance session writes atomic. Overlapping `sessions.set()` writers can still overwrite each other's whole-session changes, including drafts, even on one app instance. Converting only `resonance:update-draft` to `updateAtomic` would leave mixed writers and would not close that race. The required all-writer migration remains tracked in #313; this PR must not claim a full concurrent-write guarantee. Keep the documented single-instance deployment constraint until that migration is complete.
- Evidence: `activities/resonance/client/student/ResonanceStudent.tsx`, its decision-table and mounted regression tests, `activities/resonance/server/routes.ts`, and `.agent/plans/complete/resonance-client-draft-state-consolidation.md`.

### Accepted clear with no stored draft

- Owner: Resonance `resonance:update-draft` handler.
- Invariant: An accepted `answer: null` write advances and persists `draftOrderingWatermarks[draftKey]` before acknowledging, whether or not `responseDrafts[draftKey]` currently exists. An older message handled afterward is rejected by that persisted floor. Instructor-state broadcast still requires an actual draft deletion.
- Failure behavior: If the store write fails, the clear is not acknowledged; the client retains its unconfirmed state for retry. This closes sequential stale-message arrival after an absent-draft clear. It does not close two handlers that already hold stale whole-session clones, which requires the #313 all-writer atomic migration.
- Evidence: `activities/resonance/server/routes.ts` and the absent-clear/older-write regression in `activities/resonance/server/routes.test.ts`.

### Draft ordering keys and restart snapshots

- Owner: Resonance `resonance:update-draft` and `ResonanceStudent` snapshot merge.
- Invariant: For one question/student/run, a write with an ordering key equal to or below the retained watermark cannot replace differing content. Matching content may be acknowledged without writing again; an absent draft matches a repeated clear. A restart drops the prior local answer, then restores any current-run draft in the new snapshot. When no live run revision exists, student snapshots are ordered by delivery and observed revision watermark, never by `activeQuestionRunStartedAt`.
- Failure behavior: A conflicting draft receives no saved acknowledgement, leaving the client's retry state active. This handles sequential delivery; overlapping whole-session clones remain subject to #313.
- Evidence: the equal-key and clear retry tests in `routes.test.ts`, the restart draft test in `ResonanceStudent.test.ts`, and the revision-based stale refresh test in `useResonanceSession.test.ts`.

### Stored draft ordering validation

- Owner: Resonance session normalization in `routes.ts`.
- Invariant: Both a stored draft and a retained watermark carry an `editSequence` that is a nonnegative safe integer and a `draftSendSequence` that is a positive safe integer. Missing or malformed counters cause that record to be dropped, rather than normalized to zero. These are current required fields; no legacy draft ordering shape is supported.
- Snapshot contract: `draftEditSequences` and `draftSendSequences` expose retained per-question ordering floors for the viewer's active questions. A floor may survive a clear after `draftAnswers` loses the corresponding content.
- Evidence: `resolveStoredDraftOrdering`, its decision table and the student-state normalization regression in `activities/resonance/server/routes.test.ts`.

### Rejected draft acknowledgement precedence

- Owner: Resonance `resonance:update-draft` handler.
- Invariant: A rejected write is acknowledged as saved only when its intended state already exists. A current-run draft takes precedence over the confirmed response for the same question and student. With no current-run draft, a clear matches the absent draft; the confirmed-response staleness guard may also acknowledge content equal to that response. The watermark staleness guard has no confirmed-response fallback.
- Failure behavior: A mismatched write receives no acknowledgement and remains eligible for the sending client's retry. This does not close the overlapping whole-session clone race tracked in #313.
- Evidence: `shouldAcknowledgeRejectedDraft` decision table and the post-submission revisit route regression in `activities/resonance/server/routes.test.ts`.

### Student snapshot resync and draft settlement

- Owner: `useResonanceSession` owns full-snapshot application; `ResonanceStudent` owns each question's draft attempt record.
- Snapshot invariant: Starting a REST request does not make an older in-flight response unusable. Only an accepted newer REST or WebSocket snapshot advances the application barrier. Fallback polling remains active while the socket is disconnected and after it opens until a full post-open refresh or WebSocket snapshot is accepted. A failed post-open request leaves polling active and an older usable response eligible.
- Draft invariant: An attempt may release only its own in-flight token. Its acknowledgement is applied before a queued retry is drained. A matching acknowledgement clears `unconfirmed`, so a periodic tick queued during the send does not launch a duplicate; a changed answer remains unconfirmed and retries immediately after settlement.
- Evidence: the post-open failure/initial-response test in `useResonanceSession.test.ts` and the unchanged-tick/changed-answer settlement test in `ResonanceStudent.test.ts`.

### Deadline reconciliation requires the server's own expiry verdict

- Owner: `buildStudentSnapshotWithMode` (server) states expiry; `ResonanceStudent`'s retry-interval deadline-reconciliation branch consumes it.
- Invariant: Every student snapshot carries `activeQuestionDeadlineExpired`, true when the clock sample `loadResonanceSession` finalized against had reached `activeQuestionDeadlineAt`, and false with no deadline, in self-paced mode, or for a session that never went through that load. The snapshot builder reuses that sample (a per-clone `WeakMap`) and never takes a fresh one, because a later sample could report expiry for a clone whose drafts were not finalized. So `true` means this student's drafts for the run are already finalized. A staged run keeps its revision and deadline after expiry, so this flag is the only signal for it. The client clears unconfirmed draft tracking and discards its local answer only when a refreshed snapshot has `activeQuestionDeadlineExpired`, or the run/deadline being reconciled was replaced or ended (`isServerPastReconciliationDeadline`). A successful `refresh()` alone proves only that a snapshot was accepted; the client's own clock can be ahead of the server's. Inferring finalization from a confirmed response is unsound: a revisit leaves an earlier response behind, and another tab can confirm the same edit sequence with different content.
- Failure behavior: While the server has not reported expiry, tracking is left untouched, retries continue, and `reconciledExpiryRef` is not set, so the next tick refreshes again rather than discarding an answer the server would still accept.
- Evidence: `isServerPastReconciliationDeadline` decision table and the mounted "does not discard the local answer" test in `ResonanceStudent.test.ts`; "student snapshots report the server-side deadline expiry" in `routes.test.ts`; "a snapshot never reports expiry from a later clock sample" (fails if the builder resamples).
- History (Copilot/CodeRabbit reviews on PR #381, 2026-09-24): this replaced three successively unsound client-side proxies for finalization (an accepted `refresh()`, membership in `submittedAnswers`, then a confirmed edit sequence), per AGENTS.md rule 16.

### Same student in two tabs: ordering is client-assigned, and a short deadline can outrun the ratchet (accepted limitation)

- Owner: Resonance `resonance:update-draft` handler and `ResonanceStudent`.
- Decision: `draftSendSequence` is a per-mount counter, so a second tab of the same student can send the same `editSequence` with a lower `draftSendSequence` than the first tab's watermark. The handler rejects that write without acknowledging it (content-aware acknowledgement, Follow-up 12 item 2), and the sender keeps retrying with an incrementing counter until it passes the watermark or a snapshot ratchets it (post-open refetch, Follow-up 16). If the deadline expires before that, the other tab's stored draft is what gets finalized. This is accepted: it needs one student with two live tabs editing the same question concurrently plus a deadline shorter than the retry ratchet.
- Rejected alternative: server-assigned per-student/question order by arrival. Arrival order is exactly what fails when a delayed older handler resumes after a newer one, which is why the client assigns the sequence (see the ordering guard's design notes). Replacing it would reintroduce that stale-overwrite, in the far more common single-tab case, to help the two-tab case.
- Revisit only if a per-mount identity can be carried in the ordering key (for example a mount id compared with the watermark's owner) without giving up client-side ordering. Do not re-raise per review round without that design.
- Evidence: "a stale draft write from a second concurrent tab is not acknowledged as saved when its content was actually discarded" in `routes.test.ts`.
